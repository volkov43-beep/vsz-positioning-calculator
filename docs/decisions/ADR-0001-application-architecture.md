# ADR-0001 — архитектура приложения ВСЗ

**Статус — Proposed — ожидает согласования.** Предложение оформлено в 05-1. Предмет согласования — стек MVP, место выполнения расчёта и способы локального сохранения.

## Проблема

Одна правка измерения должна отразиться в настольной таблице, мобильной карточке, сводке, графике и отчёте. Инженеру важно повторно открыть исходные наблюдения и доказуемо связать каждую цифру с той редакцией, для которой она рассчитана. ВСЗ требуется обслуживать приложение на обычном хостинге, независимо проверять вычисления и демонстрировать продукт при недоступности основной площадки.

## Варианты

| Вариант | Основание для выбора или пересмотра |
| --- | --- |
| А. TypeScript, HTML/CSS и Vite | Статическое размещение и минимум зависимостей. При сохранении всех сценариев 04 синхронизацию представлений, фокуса и статусов придётся поддерживать вручную. |
| Б. React, TypeScript и Vite | Общая редакция модели обслуживает четыре экрана. Слой интерфейса использует React, то же независимое ядро запускается в браузере и на испытательном стенде. |
| В. Клиент и API на PHP или Python | Обоснован при необходимости общего архива, доступа по ролям или централизованного вычислителя. Добавляет передачу измерений, серверную эксплуатацию и зависимость расчёта от связи. |

Сравнение двенадцати критериев, включая точность и конфиденциальность, приведено в [архитектурной спецификации](../architecture/architecture.md#2-рассмотренные-технологии).

## Рекомендуемое решение

Принять за основу **вариант Б**. Поставлять HTML/CSS, React и скомпилированный TypeScript как статику. Выделить чистое TypeScript-ядро с явным методом s и версией алгоритма. Сравнивать его результаты с независимыми JSON-эталонами в Node.js. В MVP предложены IndexedDB для локального восстановления и файл для переноса испытания. Расчёт, открытие файла и формирование отчёта выполняются на устройстве инженера.

## Причины и последствия

| Преимущества | Цена решения и ограничения |
| --- | --- |
| Одна редакция входов для всех экранов. Правка ячейки делает устаревшими соответствующие итоги и отчёт. | Требуется поддерживать React, проверять фокус, мобильный ввод и отзывчивость большой матрицы. Фреймворк сам по себе доступность не обеспечивает. |
| Один вычислитель для браузера и независимого запуска в Node.js. Форматирование изолировано от расчёта. | Выбор TypeScript не устраняет потерю точности. Диагностику и сравнение локальных характеристик предстоит реализовать и проверить отдельно. |
| Статическую сборку можно размещать на Pages и на HTTPS-поддомене ВСЗ. На сервере не нужны среда выполнения приложения и база. | Первый вход требует доступной площадки. Разные адреса не разделяют локальные черновики. |
| Измерения остаются на устройстве, инженер сам решает, когда передавать файл. | Очистка браузера и потеря устройства могут уничтожить единственную локальную запись. Для переноса и восстановления нужна отдельно сохранённая копия. |

**До реализации основного расчётного ядра необходимо исправить и согласовать §9.2 и §9.4.** В P02-mixed-scale теряется локальный разброс, а широкий допуск может скрыть ложный ноль. Выбор метода s и численной политики требует отдельного согласования. [Численное заключение 03А](../validation/numerical-policy-review.md).

## Условия пересмотра

Рассмотреть А, если объём интерфейса существенно сократится и единое состояние можно будет поддерживать проще. Рассмотреть В, если предприятие потребует совместного доступа, обязательного аудируемого архива, управляемых резервных копий или централизованного расчёта. Если контрольные наборы выявят недостаточную точность либо проверка на целевых устройствах покажет неприемлемую задержку, сначала пересмотреть числовое представление или выполнение ядра в браузере. Для смены платформы нужны воспроизводимые результаты.

Владелец проекта рассматривает ADR в общем Draft PR итерации 05. Принятие архитектурного решения и метрологическое утверждение метода имеют разные основания. [Отчёт итерации](../iterations/05-architecture.md).
